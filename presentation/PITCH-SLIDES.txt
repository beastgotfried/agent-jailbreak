## Slide 2 — A Valid Score Can Hide a Changed Control

**Main message:** A guardrail can return valid numbers while its decision behavior changes.

**Slide points:**
- Traffic, model versions, wrappers, and score transformations can change guardrail behavior.
- A lower score can mean a safer request—or a changed scoring path.
- One score cannot distinguish those causes without a reference or labels.
- Veyra checks runtime consistency separately from traffic change and classifier quality.

**Simple example (illustrative, not a customer deployment):** A bank's guardrail wrapper rescales scores after a deployment. Outputs stay valid numbers, but decisions change. Veyra checks fixed probes, identifies the change, and verifies recovery.

**Technical detail:** The implemented `scale` fault multiplies guardrail scores by 0.25. Model weights and the request stream stay fixed. Other implemented faults: affine, square, clipped, constant, inverted, common-mode scaling, persistent replacement, late onset, recurrent fault.

**Actual recorded example (scale / seed 0):** healthy guardrail score 0.7426 vs rescaled 0.1856, fixed threshold 0.2083 — a valid number, a changed decision.

## Slide 3 — Separate Observation, Verification, and Authority

**Main message:** Veyra links runtime evidence to a controlled response.

**Slide points:**
- **Guardrail:** makes the allow/refuse decision under a frozen policy.
- **Canary:** supplies a second score view; it does not make the request decision.
- **Runtime check:** compares both models with fixed reference probes.
- **Response:** verifies a correction or trusted reload, or keeps the service contained.

**Authority table:**

| Component | Responsibility | Authority |
|---|---|---|
| Guardrail | Score request text; apply the binary threshold | Request decision |
| Canary | Score the same text and verification probes | Observation only |
| Passive KS monitor | Detect a distribution change in signed score gaps | Warning only |
| RuntimeWatch | Detect changed outputs on matched probes | Runtime incident evidence |
| RecoveryManager | Execute and verify candidate backends | Activation needs explicit approval |
| SupervisedRuntime | Gate requests and maintain a hold | Separate containment and release authority |

**Why useful:** A response never follows a traffic warning automatically. The runtime checks the active backend, not a stale cached candidate. A new incident can open after a verified recovery. An unsuccessful replacement leaves an explicit hold, not a false restoration claim.

```text

Three horizontal lanes: "Traffic observation" (gray), "Runtime integrity" (blue),
"Response authority" (teal). Only the runtime lane reaches a gate icon labelled
"Approval + verification". The traffic lane ends at a warning flag.
```

**Speaker notes:** "The canary is not an oracle or a second blocking filter. We keep three questions separate: Has traffic changed? Has the runtime changed? Does labelled evaluation show a quality change? This separation prevents a traffic warning from becoming an automatic model change."

## Slide 4 — The Implemented Architecture

**Main message:** The working system is a native Python execution pipeline with explicit evidence and response boundaries.

**Slide points:**
- Ordered requests enter an offline Python replay or classifier CLI.
- The supervisor checks runtime health and uses the current model backend.
- Candidate execution, paired verification, and approval precede activation.
- Local JSON/JSONL records preserve decisions, incidents, costs, and artifact identities.

**Actual flow:**
1. Validate the request and model identity.
2. Run 8 scheduled matched probes every 16 request positions.
3. Confirm a runtime incident if either score vector changes beyond 1e-8.
4. Execute an affine candidate or a trusted backend reload.
5. Verify both score vectors and decisions on 128 separate verification probes.
6. Reverify the candidate before generation-bound, single-use activation.
7. Gate the request with the current policy, or retain an explicit hold.
8. Record events and outcomes for the independent audit.

**IBM LinuxONE boundary:** data generation, model fit, inference, probes, response, replay, audit, wheel build, and release qualification all run on native `s390x`. Qualified container: two-CPU quota, 4 GiB memory. Development VM: 3 vCPUs, ~8 GiB RAM, Ubuntu 24.04.

**Status honesty:** Current interfaces are CLI and Python API. Web console, REST intake, Kafka, PostgreSQL, S3, and customer enforcement connectors are PRD roadmap items — never show them inside the implemented boundary.

## Slide 5 — Data and Models Built for a Native CPU Workflow

**Main message:** A controlled dataset and lightweight models make the runtime experiment reproducible on LinuxONE.

**Slide points:**
- **100,000 synthetic requests** with explicit intent labels and family-based splits.
- Word/character TF-IDF guardrail and character TF-IDF canary.
- Thresholds selected on validation data only; test labels never enter live decisions.
- The release selects by measured operational results, not model size.

**Dataset design:**

| Item | Value |
|---|---:|
| Total rows | 100,000 (train 70,000 / validation 10,000 / test 20,000, class-balanced) |
| Template families | 100 |
| Reviewed semantic groups | 91 |
| Target-intent combinations | 1,000 |
| Normalized duplicates / cross-split group overlap | 0 / 0 |

Rows are compositional variants, not independent human requests. Related cases stay in one split.

**Selected models:** Guardrail = word 1–2 gram + char_wb 3–5 gram TF-IDF, logistic regression C=4, threshold 0.20832091569900513. Canary = char 3–5 gram TF-IDF, logistic regression C=1, threshold 0.2771334648132324. Balanced class weights, seed 42.

**Healthy synthetic test (20,000 rows):** Guardrail — accuracy 88.665%, harmful recall 99.960%, safe FPR 22.630%, ROC-AUC 0.9917. Canary — accuracy 86.265%, recall 99.610%, safe FPR 27.080%.

**Model selection:** On the same exposed benchmark, selected TF-IDF monitored score **81.69%** vs BERT-tiny + lexical stack **78.22%**. The neural comparison catches one additional harmful test request but refuses 549 additional safe test requests. Both outcomes stay preserved; the release keeps the stronger completed operational candidate.

**External datasets (roles, not selected-model fit):** ToxicChat 0124 (CC-BY-NC-4.0) · WAInjectBench (license not verified) · JBB-Behaviors (MIT) · JailbreakBench mirror (not listed) · StrongREJECT (not listed) · HarmBench (MIT) · XSTest (CC-BY-4.0) · Dolly 15k (CC-BY-SA-3.0) · OASST1 (Apache-2.0, acquisition/schema only, evaluation paused).

## Slide 6 — Two Evidence Channels, One Clear Decision Boundary

**Main message:** A traffic warning and a runtime confirmation answer different questions.

**Slide points:**
- Compare guardrail and canary scores through a signed gap `g = guardrail − canary`.
- Empirical KS windows detect a traffic relationship change (warning only).
- Matched probes confirm changed runtime outputs (response evidence).
- Runtime evidence plus approved verification — not a KS warning — controls recovery.

**Original KS configuration (separate historical path):** window 64 / stride 16 / horizon 512 / 29 looks / 200 null episodes / threshold 0.23258359872611467. It reports a distance, not a p-value; not an anytime-valid guarantee.

**Selected runtime configuration:** 8-probe health panel · cadence every 16 requests · tolerance 1e-8 · 64 fit probes / 128 verification probes · supervisor budget 128 incidents.

**Scan martingales:** **Not implemented in Veyra.** Present in the Cheap Canaries reference (conformal p-values, betting evidence, union-bound threshold). Mention as prior art only.

**MMD:** **Not implemented in Veyra.** Reference implementation exists in Cheap Canaries (Gaussian-kernel MMD on embeddings).

**What we add beyond the inspected reference:** actual candidate execution, fresh paired verification, generation-bound single-use activation, trusted backend reload, explicit holds, repeated incidents, complete-stream exposure accounting, and native LinuxONE reproducibility. No head-to-head performance comparison is measured.

## Slide 9 — Recovery Requires Evidence, Not Optimism

**Main message:** A candidate becomes active only after the system verifies the actual replacement behavior.

**Slide points:**
- Fit a correction only from a separate trusted probe set.
- Execute candidates on disjoint verification requests.
- Check both models, decisions, and class-specific outcomes before activation.
- Keep containment explicit; require full verification before release.

**Implemented workflow:** confirm change → explicit approval and actor → bounded affine fit (`healthy ≈ slope × current + intercept`) → verify within 1e-8 on both score vectors → manager-owned single-use plan → fresh re-verification immediately before activation → trusted backend reload as the alternative → hold if nothing passes → explicit approved release after full paired verification.

**Affine recovery vs recalibration:** selected recovery never changes weights or the policy threshold. The separate earlier conformal experiment computes class-conditional prediction-set quantiles from labelled calibration rows; all eight candidate applications stayed blocked by the fixed verification gate (harmful-class review 92% vs 75% ceiling). That result demonstrates rejection behavior, not successful recalibration. The current binary policy makes no conformal coverage claim.

**Reliability controls (test-backed):** actual candidate execution, single-use manager-bound plans, whole-pair verification, no response on matching probes, traffic warnings cannot consume a later runtime response, new incidents after verified release, verified restart when current output is unavailable, separate containment approval, redacted error reporting.

**Validation scope (state honestly):** recovery restores the tested baseline, not universal semantic correctness. Finite probes can miss input-specific or probe-evading faults. Guardrail and canary share data and one estimator family (healthy error correlation 0.7888; both wrong on 2,033/20,000). Offline approval flags exist; production authentication, durable incidents, and connectors are not implemented. Digests detect changed bytes; they are not signatures or hardware attestation.

## Slide 10 — Native IBM Z Execution, Evidence-Backed Control

**Main message:** Veyra demonstrates a complete guardrail-integrity workflow on the native platform where enterprise Linux AI runs.

**Slide points:**
- Data generation, model fit, inference, checks, recovery, and audit run natively on LinuxONE.
- The selected workflow reproduces in a fresh container with networking disabled.
- Model artifacts and request data stay in the private execution environment.
- Platform, safety, and model-risk teams get a traceable response decision.

**Why LinuxONE matters here:** big-endian `s390x` execution is demonstrated, not assumed — no x86 emulation. The full loop runs with no external model API once artifacts are present. Reproduction matches all data bytes, learned model state, request scores, decisions, response actions, and benchmark metrics (156 byte-identical algorithm files; serialized model bytes can differ only in scikit-learn's process-local cache field, while the distributed model file keeps its fixed hash).

**Verified platform facts:** Python 3.12.15 · NumPy 2.0.2 · SciPy 1.13.1 · scikit-learn 1.9.0 · joblib 1.6.0 · (neural comparison: PyTorch 2.11.0+cpu, Transformers 5.19.0) · native tests 292 pass / 4 optional skips · selected fit 39.82 s · peak child RSS 923.84 MiB.

**Platform scope:** Telum/Spyre acceleration, Secure Execution, hardware attestation, z/OS, HA, and IBM certification are not implemented or measured. No LinuxONE-vs-x86 speed claim.

**Target users (proposed, not measured customers):** AI platform engineers (validate runtime changes) · LinuxONE platform operators (qualify a local CPU safety workflow) · trust & safety analysts (separate traffic warnings from runtime incidents) · model-risk reviewers (examine recovery evidence).

**Closing line:** **"A guardrail needs a watcher. On LinuxONE, we make that watcher measurable — and every recovery verifiable."**
